## Context

参见 `proposal.md`。现有界面已经有浅深主题 token、侧栏品牌区和统一的全局 CSS，但品牌图标由通用 Lucide 图标组合而成，应用窗口尚未配置专用图标资源，表面样式也主要为不透明纯色。

## Goals / Non-Goals

**Goals:**

- 用一个可打包的位图应用图标和对应的轻量前端标记建立一致品牌识别。
- 将全局颜色变量升级为浅深色半透明视觉 token，保持聊天、设置和编辑器的一致层级。
- 保持现有交互、响应式断点、可访问焦点和文本/代码对比度。

**Non-Goals:**

- 不重做导航信息架构、会话数据或 Claude 执行流程。
- 不将内容区改造成装饰性营销布局，也不引入背景插画、渐变光球或新的 UI 依赖。
- 不复制用户提供的参考位图；只采用其橙色放射终端的视觉方向。

## Decisions

### 决策 1：一套源位图服务窗口和打包图标，前端使用可缩放图标结构

使用生成的高分辨率 PNG 作为打包源，再在构建期产出 macOS `.icns`、Windows `.ico` 和 Linux/通用 PNG。侧栏以 CSS 和 Lucide 组合表达同一方向，避免将低分辨率应用图标嵌入常驻页面。这样窗口、Dock 和打包产物使用可靠的原生格式，UI 标记在不同尺寸下依旧清晰。

备选方案是在页面和应用窗口均使用单一 SVG。它能简化源文件，但 Windows/macOS 打包格式与平台图标缓存会增加发布不确定性，因此不采用。

### 决策 2：以 token 化的玻璃表面取代局部 opacity

在根主题变量中定义 canvas、sidebar、surface、inset、border 和 shadow 的透明度与背景混合方式；现有组件继续消费 token，仅对关键容器补充 `backdrop-filter`。浅色使用暖白与冷灰的轻层，深色使用近黑蓝灰层，并保留蓝色操作强调与橙色品牌强调的职责分离。

备选方案是给每个组件单独加半透明背景。它会导致浅深主题不一致并增加回归成本，因此不采用。

### 决策 3：视觉更新保持工作区克制

聊天正文和工具活动保持无装饰的阅读布局；半透明效果集中在导航、标题、编辑器和少量浮层。活动组与设置行沿用细边框、5-8px 圆角和稳态尺寸，避免嵌套浮卡。

## Risks / Trade-offs

- [背景透明度过高导致文字对比度不足] → 为 Markdown、代码、输入和危险状态保留不透明或高对比 token，并在浅深主题截图中检查。
- [macOS/Windows 图标格式生成不一致] → 使用同一 PNG 源在本机构建前生成各平台格式，并在 Electron 窗口显式引用。
- [backdrop-filter 在部分环境不可用] → 每个表面保留不透明回退背景，视觉层级仍然成立。
- [全局 token 改动影响旧页面] → 保持 token 名称和组件结构，使用完整测试、生产构建和响应式截图验证。

## Migration Plan

1. 添加品牌源图及目标平台图标资源，配置 Electron 窗口和打包元数据。
2. 更新侧栏品牌组件和全局浅深主题 token，再逐项校正标题、编辑器、设置和输出表面。
3. 增加视觉资源与布局回归测试，执行测试、类型检查、构建和手工截图检查。
4. 回滚时移除图标配置并恢复原有 token；不涉及数据迁移或会话兼容性。
