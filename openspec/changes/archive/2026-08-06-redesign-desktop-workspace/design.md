## Context

当前渲染层使用一套深色 CSS 变量，但 `SessionList`、`ChatView`、`Composer`、`MessageBubble` 和确认框仍写有大量内联颜色值；代码高亮固定为深色主题。应用的本地持久化目前仅覆盖会话数据，预加载层也尚未暴露应用偏好接口。参见 proposal.md 与本变更的两份规格。

现有 `gui-chat`、`session-management` 和 `model-switching` 仍处于未归档的应用初始变更中。因此本变更的工作台行为作为独立能力定义，且不得修改 CLI 调用、会话文件格式或流式消息组装逻辑。

## Goals / Non-Goals

**Goals:**

- 建立可在浅色、深色和跟随系统之间切换的完整主题体系，并保存用户偏好。
- 让侧栏、空会话、消息工作区和输入区形成稳定的桌面信息层级。
- 将颜色和状态样式从组件内联值迁移到可复用的语义化令牌，避免主题切换出现遗漏。
- 保持现有会话、流式生成、模型选择、权限模式和消息操作的行为不变。

**Non-Goals:**

- 不增加云同步、账号、主题商店或可自定义调色板。
- 不改变 Electron 窗口装饰、CLI 权限语义、会话数据格式或 AgentTransport。
- 不在本变更中实现移动端布局；窗口最小尺寸沿用现有桌面约束。
- 不复制 Codex 的品牌、文案或专有图形资产，只借鉴其信息层级与工作流结构。

## Decisions

### 决策 1：主题偏好由主进程持久化，渲染层只消费有效主题

保存值为 `light`、`dark` 或 `system`，缺失或无效值等同于 `system`。主进程在用户数据目录维护独立、原子写入的应用偏好文件，通过受控 IPC 暴露“读取偏好”“更新偏好”和“有效主题变化”三个最小接口；渲染层不直接写磁盘。

当保存值为 `system` 时，主进程使用 Electron 的系统外观能力计算有效主题，并在系统外观变化时向渲染层推送。渲染层将有效主题挂到根元素的 `data-theme` 属性，令所有页面在同一个渲染周期内切换。

选择主进程持久化而非 `localStorage`：与会话数据一样跨窗口、打包和清理策略更可控，且符合现有 contextBridge 边界。`localStorage` 虽实现更短，但会使用户设置与应用本地数据分裂，也不适合从主进程订阅系统外观事件。

将首次偏好设为 `system` 而不是直接写入首次启动时的有效主题：用户尚未做出手动选择时，应用应继续响应后续的系统偏好变化，而不是将首次检测结果意外固化为手动主题。

### 决策 2：以语义化设计令牌取代组件内的视觉常量

`App.css` 定义表面、文本、边框、焦点、主操作、危险、成功、警告和代码块等语义令牌；`[data-theme="light"]` 与 `[data-theme="dark"]` 分别赋值。浅色为默认白色画布与浅灰导航，主操作采用蓝色；深色使用中性炭灰表面并保留独立的状态色，而非反转浅色值或延续紫色主色。

组件以 className 与令牌表达状态，只有与动态内容直接相关的尺寸或位置保留内联样式。弹窗、输入、菜单、工具调用、错误和中断状态必须同样迁移。

选择令牌体系而非为每个组件维护两套 CSS：新增状态或组件只需连接语义角色，避免主题间漏改。完全保留内联样式会使主题逻辑分散且难以视觉回归。

### 决策 3：工作台由壳层、会话导航、聊天状态与组合器四层组成

渲染布局收敛为：固定侧栏负责产品入口、会话列表与底部设置；主工作区负责当前会话；聊天视图在“空会话起始区”和“消息阅读列”之间切换；贴底组合器独立于消息滚动。会话标题、模型、权限状态在组合器上方的上下文条内展示，避免当前工具栏占据输入框上方的整行空间。

空会话起始区使用四项 Claude Code 本地开发任务建议：“探索当前项目”“规划一次改动”“定位并修复问题”“审查当前工作区”。每张卡片以标题和一行任务说明组成紧凑信息组，避免当前仅有图标和标题时形成大面积无信息留白。选择卡片只写入组合器草稿并聚焦，绝不自动调用 CLI。为此，将草稿状态提升到聊天视图（或等价的局部工作区状态），通过受控 props 传递给组合器，避免跨组件 DOM 引用或全局临时状态。

选择“受控草稿 + 局部工作区状态”而非直接由欢迎卡片触碰 textarea：它保留 Enter 发送、自动伸缩、停止生成等既有行为，并在会话切换时有清晰的归属。

任务建议不是功能入口或快捷执行命令，而是可编辑的首条任务草稿。因此文案使用当前工作区、变更计划、问题根因和 Git 工作区等 Claude Code 常见上下文，不承诺应用不能直接验证的特定结果。

### 决策 3a：组合器保持稳定表面，将编辑与提交操作分层

组合器沿用上下文状态条和受控草稿，但输入表面采用内侧编辑区与固定尺寸操作区：textarea 只负责内容与高度增长，发送和停止按钮共享稳定的容器尺寸。焦点环绘制在整体输入表面，提交可用性以 `disabled`、颜色和原生可访问名称共同表达。不会增加显性快捷键提示，以免在高频输入区增加噪音。

这种处理比为生成态、空草稿和多行草稿分别创建不同布局更稳定，能避免按钮状态切换时改变消息区和输入区之间的垂直节奏。

### 决策 4：图标与代码高亮都是主题系统的一部分

操作按钮使用统一图标库并提供原生 tooltip 或等价可访问名称；文字仅用于需要明确确认的命令。图标颜色来自语义令牌，不能作为唯一状态表达。

Markdown 高亮不再全局固定导入深色样式。主题提供者根据有效主题加载匹配的浅色或深色高亮样式，代码块背景与复制按钮也通过令牌控制。这样浅色工作台不出现孤立的深色语法主题，同时深色模式仍保留代码可读性。

### 决策 5：设置使用侧栏底部的轻量菜单，不引入独立设置页

侧栏底部的齿轮入口打开锚定式设置菜单，其中使用三态选项选择外观。菜单显示当前偏好和在 `system` 下的有效主题；点击菜单外或按 Escape 关闭。主题是当前唯一的全局偏好，独立设置页会为单一操作增加不必要的跳转与维护面。

## Risks / Trade-offs

- [主题切换遗漏内联颜色或第三方样式] → 先完成令牌清单，再以浅色和深色分别覆盖消息、代码、工具、错误、确认框和禁用态的视觉回归。
- [系统主题事件导致渲染与保存偏好不一致] → 保存“偏好”而不是“有效主题”；只在 `system` 偏好下响应系统事件，手动选择保持稳定。
- [欢迎卡片草稿与会话切换混淆] → 草稿生命周期归属当前聊天视图，会话切换时显式重置或恢复已定义的草稿状态，不将其写入消息历史。
- [UI 重构影响流式滚动或停止操作] → 保持 Zustand 生成状态和 TurnAssembler 不变，为长会话、工具穿插和生成中主题切换做回归验证。
- [新增图标依赖增加打包体积] → 仅按需导入常用图标，并在打包产物中检查依赖没有影响 Electron 主进程。

## Migration Plan

1. 发布后，不存在偏好文件的现有安装自动以跟随系统启动；已经保存浅色、深色或跟随系统偏好的安装保持原选择。现有会话索引和会话文件不迁移。
2. 用户首次在设置中选择外观时创建偏好文件，写入失败时保留当前已渲染的主题并显示可理解的保存失败提示。
3. 回滚版本可忽略偏好文件；由于本变更不修改会话数据，用户会话和 CLI 上下文无需恢复操作。
