## 背景

本变更的动机与范围见 `proposal.md`。当前仓库已经有可运行的 Electron + React 应用和较完整的实现注释，但根目录 README 尚未形成入口；现有设计和验收文档也混合了历史目录、当前实现和待验证事项。文档必须以当前代码和 `package.json` 为准，并遵守 `CLAUDE.md` 的中文 OpenSpec 文档约定。

## 目标 / 非目标

**目标：**

- 让首次阅读者能从 README 完成“安装依赖 → 检查 Claude CLI → 启动开发模式”的最短路径。
- 用稳定的文档分层解释用户工作流、代码架构、测试与发布验收，并通过相对链接互相导航。
- 准确描述主进程、Preload、渲染层、IPC、Claude 子进程、流式事件组装和 JSON 持久化之间的关系。
- 记录项目目录、Skills、模型/权限、外观/语言、会话、桌面斜杠命令等已经存在的能力边界。
- 将命令、版本、目录和验收状态与仓库事实对齐，便于后续变更复核。

**非目标：**

- 不修改 TypeScript/React/Electron 代码、IPC 名称、数据格式、依赖或打包配置。
- 不在本次变更中实现自动发布、文档站点、国际化翻译或新的端到端测试框架。
- 不把 `docs/ai-usage.md` 的开发过程记录改造成用户操作手册。
- 不声称尚未完成的 Windows/Linux 实机验收已经通过。

## 决策

### 1. README 作为入口，细节下沉到按受众划分的文档

README 保留项目定位、能力摘要、快速开始、常用命令、数据与安全提示和文档索引；完整操作步骤放入 `docs/getting-started.md`，贡献者流程放入 `docs/development.md`，故障排查放入 `docs/troubleshooting.md`。

这样可以让首页保持可扫描，同时避免把架构细节和排障段落复制到多处。备选方案是把所有内容塞进单个 README，成本低但难以维护，也不利于区分用户和开发者信息。

### 2. 以代码和脚本为文档事实来源

实现文档按以下顺序复核：

1. `package.json` 的 scripts、依赖版本和 electron-builder 产物配置。
2. `electron/main.ts`、`electron/preload.ts`、`src/ipc.ts` 的进程边界和 IPC 表面。
3. `electron/cli/`、`electron/store/`、`src/store/` 与组件目录的职责。
4. `tests/` 的测试文件和 fixture，作为已覆盖行为的证据。

文档中的命令必须直接对应 scripts；目录说明只保留当前存在且对读者有帮助的入口。对于会随版本变化的 Claude CLI 行为，使用“当前验证版本/以本机 `claude --version` 为准”的措辞，而不是硬编码未来保证。

### 3. 采用“架构说明 + 使用指南 + 排障 + 验收”四层结构

- `docs/design.md`：维护模块职责、数据流、安全边界、持久化和明确的主动放弃项。
- `docs/getting-started.md`：维护前置条件、首次启动、项目目录和核心工作流。
- `docs/development.md`：维护本地开发、测试、调试、代码约定和提交前检查。
- `docs/troubleshooting.md`：维护按症状组织的诊断步骤和平台差异。
- `docs/validation-matrix.md`：维护自动化检查与三端人工验收的状态，不重复用户教程。
- `docs/ai-usage.md`：保留为历史开发记录，并由 README 明确标注。

备选方案是只更新现有三个 docs 文件，但会继续让使用者、贡献者和发布验收共用同一篇长文，信息架构问题不会真正解决。

### 4. 对安全和数据边界做显式说明

README 和 getting-started 只描述“通过本地 `claude` 子进程通信、不直接调用 Anthropic API”“项目路径由主进程选择并在发送前复核”“会话/外观/语言数据写入 Electron userData”。不记录真实 token、环境变量值或用户项目内容；故障排查仅给出脱敏日志和路径检查方法。

### 5. 用轻量校验保证文档可维护

实现阶段不新增依赖。完成文档后执行：链接和路径人工检查、`rg` 对照脚本/目录、`npm run typecheck`、`npm test` 和必要时 `npm run build`。验证结果写回 validation matrix 的“已验证实现细节”或“待验证项”，不把文档检查伪装成跨平台实机验收。

## 风险 / 权衡

- [代码演进导致文档再次过时] → 在 development 和 README 中列出文档事实来源与提交前复核清单；避免复制过多实现细节。
- [不同平台命令/路径存在差异] → 使用平台分组表格，明确 Windows 打包需在 Windows 执行，并保留实机验收状态。
- [读者误以为 GUI 支持全部 Claude Code 斜杠命令] → 在使用指南中列出桌面端固定命令和被阻止的配置变更类别，说明未知 Skill 命令仍交给 CLI。
- [文档示例泄露敏感信息] → 示例使用占位符和脱敏输出，排障章节禁止粘贴 token、settings 敏感字段或完整项目内容。
- [新增文档造成入口过多] → README 只保留一个按受众分组的索引，其他文档互相链接但不重复导航树。

## 迁移计划

1. 按本文档结构创建或更新 README 与 `docs/` 文件。
2. 用源码和脚本逐项复核命令、路径、能力边界与状态标记，修正设计和验收文档中的过期内容。
3. 执行文档链接检查及现有 typecheck/test/build 命令，将结果记录在 validation matrix。
4. 发布时只需提交文档变更；如发现事实不一致，回滚对应文档提交即可，不涉及数据迁移或运行时回滚。
